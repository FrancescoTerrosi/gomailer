# PEC — Posta Elettronica Certificata

Sender-side compliance requirements implemented by this project.

## Normative references

| Reference | Description |
|-----------|-------------|
| DPR 11 febbraio 2005, n. 68 | Enabling regulation for certified email (PEC) |
| DM 2 novembre 2005 | "Regole tecniche" — the technical rules |
| AgID determinations | Successive amendments by Agenzia per l'Italia Digitale |
| RFC 6109 | Informational IETF mapping of PEC onto SMTP/MIME |

A PEC message is an ordinary RFC 5322/MIME message carried over an encrypted
SMTP channel, distinguished by a small set of extra headers (the "busta di
trasporto") and a well-defined receipt flow. What follows is what a **sender**
must produce; the receipts themselves are generated by the PEC providers.

---

## 1. Transport — TLS is mandatory

- The entire SMTP session **must** be encrypted. Plaintext SMTP is not allowed.
- Implicit TLS (SMTPS) on port `465`, or `STARTTLS` on `587`.
- The server certificate **must be verified** against the provider hostname
  (`InsecureSkipVerify` is for local testing only).
- Minimum TLS version 1.2.

## 2. Certified identity

- The `MAIL FROM` envelope sender and the `From:` header **must** be the
  authenticated PEC mailbox address.
- The mailbox address *is* the certified legal identity — a free-form display
  name is not a substitute and must not diverge from the mailbox.
- `RCPT TO` must contain the recipient certified addresses.

## 3. Mandatory headers (busta di trasporto)

| Header | Value | When |
|--------|-------|------|
| `X-Trasporto` | `posta-certificata` | **Always** — the single discriminator that marks the message as certified; without it the MTA treats it as ordinary email |
| `X-TipoRicevuta` | `completa` \| `breve` \| `sintetica` | Always — selects the requested receipt type (default `completa`) |
| `X-Riferimento-Message-ID` | `<message-id>` | Only when replying to a prior PEC — references the original `Message-ID` |
| `X-Ricevuta` | receipt type | Set by the **receiver** when generating receipts, never by the sender |

## 4. Receipts (ricevute)

Generated by the PEC providers, not by the sender's code. The sender only
selects the type via `X-TipoRicevuta`:

| `X-TipoRicevuta` | Receipt content |
|------------------|-----------------|
| `completa` | Full original message embedded in the receipt |
| `breve` | Original headers + digest |
| `sintetica` | Essential delivery data only |

Receipt kinds emitted downstream (for reference, via `X-Ricevuta`):

- `accettazione` — acceptance by the sender's provider
- `avvenuta-consegna` — delivered to the recipient mailbox
- `mancata-consegna` — non-delivery
- `errore-consegna` / `preavviso-errore-consegna` — delivery error / pre-notice
- `anomalia` — anomaly

## 5. Message structure & MIME

- No attachments: single-part `text/plain; charset=UTF-8`.
- With attachments: `multipart/mixed` — text part first, each attachment after.
- Each attachment carries `Content-Type`, `Content-Disposition: attachment`,
  and `Content-Transfer-Encoding: base64`.
- Base64 content is line-wrapped at 76 characters (RFC 2045), and any text
  body whose lines would exceed SMTP's 998-octet limit switches to base64
  — no line in a built message can break delivery on a strict MTA.
- Mandatory headers present on every message: `From`, `To`, `Subject`, `Date`,
  `Message-ID`, `MIME-Version: 1.0`.

## 6. Message-ID & Date

- `Message-ID` must be globally unique, RFC 5322 form `<local@domain>`, with
  the right-hand side derived from the sender's own domain.
- `Date` must be present, RFC 5322 form (`Mon, 02 Jan 2006 15:04:05 -0700`).

## 7. Header encoding

- Non-ASCII header values (`Subject`, display names, filenames) must be
  RFC 2047 encoded (`=?UTF-8?B?...?=`).
- Non-ASCII bodies are `base64` encoded; ASCII bodies stay `7bit`.

## Mapping to this codebase

| Requirement | Implementation |
|-------------|----------------|
| 1. TLS only | `mailer.go` → `connect`/`SendOn` (implicit TLS on `465`, `STARTTLS` otherwise), `tlsConfig` enforces TLS 1.2 + verification |
| 2. Certified identity | `mailer.go` → `Prepare` (used by `Send`) rejects `From != Username`; envelope sender = `Username` |
| 3. Mandatory headers | `pec.go` (constants) + `message.go` → `build` emits `X-Trasporto`, `X-TipoRicevuta`, and `X-Riferimento-Message-ID` when set |
| 4. Receipts | `pec.go` → `TipoRicevuta` (`completa`/`breve`/`sintetica`); provider-generated receipts are out of scope |
| 5. MIME structure | `message.go` → `build` (single-part vs `multipart/mixed`) |
| 6. Message-ID & Date | `message.go` → `GenerateMessageID`, `Date` header |
| 7. Header encoding | `message.go` → `encodeHeaderWord`, `encodeFilename`, `encodeText` (76-char-wrapped base64, over-long lines fall back to base64) + `renderSubject`/`foldAddressList` (RFC 5322 folding, no line can overflow the SMTP limit) |
